# O-list E-Commerce Analytics ETL Pipeline (Capstone Project)
An end-to-end data engineering pipeline designed to extract scattered, raw e-commerce data from the Olist Brazilian E-Commerce Dataset, clean and transform it into a structured star schema, and load it into a centralized PostgreSQL data warehouse for analytical reporting.

## Project Overview
This project addresses the challenges of dealing with fragmented retail data. It automates the process of gathering raw datasets (orders, items, customers, products, sellers, payments, reviews, and geolocation) and building a reliable, repeatable ETL pipeline that ensures data quality, consistency, and clean structure for business intelligence teams.

### Tech Stack
- **Language:** Python 3.10+
- **Data Manipulation:** `pandas` (v2.2.2)
- **Database Connection:** `SQLAlchemy` (v2.0.35) & `psycopg2-binary` (v2.9.9)
- **Environment Management:** `python-dotenv` (v1.0.1)
- **Formatting & Reports:** `tabulate` (v0.9.0)
- **Containerization:** Docker (PostgreSQL 15-alpine instance)

## Progress Milestones

### Week 1: Ingestion & Staging Setup (Extract Layer)
The first milestone successfully established the framework infrastructure to secure raw inputs:
*   **Infrastructure Setup:** Spun up a lightweight PostgreSQL 15 database instance using a Docker container, isolating storage with managed volumes.
*   **Strict Ingestion Layer (`extract.py`):** Configured a centralized `SCHEMA` mapping with explicit data types (like setting zip codes and IDs as `string`) to prevent typical pandas parsing issues.
*   **Automated Data Profiling:** Implemented profiling algorithms that automatically calculate row counts, exact row duplicates, and specific missing value percentages, saving them directly into a clean Markdown report (`raw_data_profile_report.md`).
*   **Staging Load Automation (`run_extract.py`):** Developed an end-to-end runner script that automatically creates a secure staging environment (`staging` schema), streams all 9 raw CSV files, chunks them in batches of 10,000 records, and safely loads them into the staging schema with robust exception logging.

### Week 2: Star Schema Architecture & Data Quality Guardrails (Transform Layer)
The second milestone extracts data from staging, handles analytical anomalies, enforces validation rules, and builds a performant data warehouse structure:
*   **Dimensional Modeling (Star Schema):** Designed and deployed a multi-tier warehouse architecture inside the `warehouse` schema consisting of:
    *   `fact_orders`: Consolidated transaction framework optimized to resolve relationship structures. Aggregates review data and leverages a **proportional payment allocation map** to effectively prevent the common revenue inflation bug caused by unchecked many-to-many joins.
    *   `dim_customers` / `dim_products` / `dim_sellers`: Structured dimension entities tracking operational records. The product master handles translations using `product_category_name_translation.csv` and preserves historical tokens if maps are missing.
    *   `dim_date`: An explicit calendar dimension with generated keys (`%Y%m%d`), days, months, years, quarters, and weekday flags to enable rapid time-series querying.
*   **Modular Transformation Design (`transform.py`):** Built structured pipeline routines to process variables step-by-step:
    *   `convert_dtypes`: Handles timestamp properties and casts prices and freights to numeric formats.
    *   `remove_duplicates`: Performs identity checks to clear identical matches while logging changes.
    *   `handle_null_values`: Drops rows missing critical identifiers (`order_id`, etc.), while populating descriptive placeholders like `missing_category` or `Unknown` for descriptive text attributes.
    *   `add_derived_columns`: Calculates operational KPIs including `delivery_delay_days` (clamped at 0 for early shipments), `total_order_value`, and flags customer sentiment with `is_positive_review`.
*   **Assert-Driven Quality Assertions:** Implemented strict constraint checks using conditional statements that prevent pipe runs if financial anomalies, future timelines, invalid delivery ranges, or orphan records are detected.
*   **Orchestration Engine & Summary Profile (`run_transform.py`):** Built an automated driver file that runs processing tasks end-to-end, creates the warehouse schema, and exports a profiling breakdown to `reports/data_quality_report.csv`.

## Getting Started

### 1. Prerequisites
Make sure you have **Python 3.10+** and **Docker Desktop** installed on your system.

### 2. Infrastructure Setup (Database)
Create a `.env` file in the root folder with your database credentials:
```env
DB_USER=your_username
DB_PASSWORD=secure_password123
DB_NAME=olist_ecommerce_etl_db
DB_HOST=localhost
DB_PORT=5433
```
Launch the staging database container using Docker:
```bash
docker compose up -d
```

### 3. Installation & Setup
Set up your isolated Python environment and install the required dependencies:
```bash
python -m venv venv
source venv\Scripts\activate
pip install -r requirements.txt
```

### 4. Running the Pipelines

#### Step A: Execute Extraction (Week 1 Ingestion)
To read the raw source files, generate preliminary metrics profiles, and populate the staging database tables:
```bash
python extract/run_extract.py
```
*Monitors structural progress outputs under `logs/extract_pipeline_logs.log`.*

#### Step B: Execute Transformation (Week 2 Data Warehousing)
To ingest data from staging, run cleaning methods, validate rules, and build your relational tables:
```bash
python run_transform.py
```
*Outputs verification reports inside `reports/data_quality_report.csv` and details pipeline execution tracking in `logs/transform_pipeline_run_proof.log`.*
